# Taxi-Talk 요구사항 명세서 (Requirements)

## 0. Intent Analysis 요약
- **User Request**: "Using AI-DLC, Taxi-Talk 기획서 기반으로 앱 만들어줘." + "현대차 공모전(Pleos App Market)에 제출"
- **Request Type**: New Project (greenfield)
- **Scope Estimate**: System-wide (신규 차량용 앱 전체)
- **Complexity Estimate**: Complex (실시간 음성 통역, 좌석 분리, 차량 데이터 연동)
- **제출 맥락**: 현대자동차그룹 차량용 앱 개발 공모전 "Code your App into Pleos App Market" (접수 ~2026.11.15, 1차 서류 11/23, 2차 오프라인 PT 12/3~4). 평가 핵심은 "차량 데이터·기능·이동 상황 활용".

## 1. 제품 개요
Taxi-Talk는 택시 운전자(한국어)와 외국인 승객(영어/일본어/중국어) 간의 언어 장벽을 해소하는 **차량 특화 양방향 실시간 통역 앱**이다. 현대차 Pleos Playground 플랫폼(Android)에서 동작하며, Pleos Vehicle SDK로 차량 데이터(할증·하차·주행·좌석 정보)를 활용해 승객의 언어로 선제적 안내를 제공한다. 좌석 역할(운전석/뒷좌석)에 따라 화면과 음성 출력을 분리하여 운전자의 주의 분산을 최소화한다.

## 2. 대상 플랫폼 및 기술 전제
- **플랫폼**: Hyundai Pleos Playground — Android (Kotlin + Jetpack Compose)
- **Vehicle SDK**: `ai.pleos.playground:Vehicle:2.3.2` (typed API)
- **빌드/실행**: Android Studio, JDK 17, Gradle, Pleos 에뮬레이터 또는 호환 차량
- **minSdk 23 / targetSdk 35** (샘플 기준), Compose 기반 UI
- **음성 처리**: Android 온디바이스 — `android.speech`(STT), `TextToSpeech`(TTS), ML Kit On-Device Translation(번역)
- **데이터 영속성**: 세션(메모리) 중심, **음성/대화 원문 미보관** (기획서 취지)
- **네트워크**: 번역은 ML Kit 온디바이스 모델 사용(최초 모델 다운로드 제외 오프라인 동작 지향)

## 3. 사용자 및 역할
| 역할 | 언어 | 주요 접점 | 설명 |
|---|---|---|---|
| 운전자(Driver) | 한국어 | 운전석 디스플레이(앞) | 주행 집중, 최소 조작. 승객 발화의 한국어 통역을 듣고/본다 |
| 승객(Passenger) | EN/JA/ZH | 뒷좌석 뷰(모사) | 언어 선택/동의, 통역·차량 안내를 자국어로 받는다 |

## 4. 기능 요구사항 (Functional Requirements)

### FR-1. 탑승 및 개인화 설정 (기획서 ①, 답변 Q4-C)
- FR-1.1 승객은 앱 시작 시 언어를 **직접 선택**(EN/JA/ZH)할 수 있다.
- FR-1.2 승객의 **첫 발화로 언어를 자동 인식**하고, 인식 결과를 화면에 표시하여 확인/변경할 수 있다.
- FR-1.3 통역 서비스 이용 **동의**(개인정보/음성 처리) 후 개인화 음성 환경이 활성화된다.
- FR-1.4 QR 스캔 진입 시나리오를 UX로 지원(딥링크/초기 화면 진입점)하되, 실제 QR 발급은 범위 외.

### FR-2. 좌석별 양방향 실시간 통역 (기획서 ②, 답변 Q4-A)
- FR-2.1 운전자 한국어 발화 → 승객 언어로 통역하여 **뒷좌석 뷰/채널**로 출력(텍스트+TTS).
- FR-2.2 승객 발화(EN/JA/ZH) → 한국어로 통역하여 **운전석 뷰/채널**로 출력(텍스트+TTS).
- FR-2.3 통역 결과는 **원문과 번역문을 함께 표시**하여 상호 확인(특히 목적지/지명 오역 방지).
- FR-2.4 발화 주체(운전자/승객)에 따라 **출력 대상 채널을 분리**한다(SSZ 소프트웨어 모사, 답변 C4-A).
- FR-2.5 통역 세션은 턴 기반(발화→인식→번역→출력)으로 상태를 관리한다.

### FR-3. 차량 정보 번역 안내 (기획서 ③/⑤, 답변 Q4-B)
- FR-3.1 사전 정의된 차량 안내 메시지를 승객 언어로 제공한다. 최소 포함:
  - 안전벨트 착용 요청
  - 도착 예정 시간 안내
  - 심야/지역 **할증** 적용 안내
  - **하차 안내**("오른쪽 문으로 내려주세요") 및 소지품 확인
- FR-3.2 안내 메시지는 **차량 데이터 이벤트와 연동**되어 적절한 시점에 트리거된다(FR-5 참조).
- FR-3.3 안내 메시지는 텍스트 표시 + 뒷좌석 채널 TTS로 전달된다.

### FR-4. 주행 중 상황 안내 (기획서 ③, 답변 Q4-D)
- FR-4.1 경로 변경/교통 정체/예상 도착시간 변경 발생 시 승객 언어로 안내한다.
- FR-4.2 주행 중 운전석에는 통역·필수 안내를 우선 제공하고, 뒷좌석에는 번역 안내를 제공한다.
- FR-4.3 중요한 차량 안내 또는 통역이 필요한 경우 뒷좌석 부가 출력을 **일시 중지/감쇠**한다.

### FR-5. 차량 데이터 연동 (공모전 평가 핵심, 답변 C5-A)
Pleos Vehicle SDK 2.3.2 도메인을 활용한다. SDK 미지원/미연결 시 **소프트웨어 모사(fallback)** 로 동작한다.
- FR-5.1 **Toll** 도메인 → 할증/통행료 상태를 읽어 할증 안내(FR-3.1) 트리거.
- FR-5.2 **Door / Window** 도메인 → 정차/하차 시 하차 안내(FR-3.1) 트리거(하차 방향).
- FR-5.3 **Driving mode / Odometer / Car info** → 주행 상태·도착 정보 안내(FR-4) 트리거.
- FR-5.4 **Seat** 도메인 → 좌석(운전석/뒷좌석) 컨텍스트로 채널 분리 보조.
- FR-5.5 모든 SDK 호출은 샘플 패턴을 따른다: `initialize()` → capability check → read/register → `release()`, 비동기 콜백 기반, capability 범위 검증 후 제어.

### FR-6. 목적지 도착 및 안전 하차 (기획서 ⑤, 답변 Q4-F)
- FR-6.1 목적지 접근 시 예상 도착 시간 및 하차 정보를 승객 언어로 안내.
- FR-6.2 도착 후 소지품 확인 및 안전 하차 유도 메시지 출력.
- FR-6.3 필요 시 목적지/운행 정보를 재확인할 수 있다.

### FR-7. 범위 제외 (Out of Scope — MVP)
- 승객 맞춤형 지역 관광 오디오 콘텐츠(기획서 ④, Q4-E 미선택).
- 실제 QR 코드 발급/서버, 결제/요금 정산, 실제 SSZ 하드웨어 드라이버 제어.
- 대화/음성 데이터의 서버 저장 및 분석(미보관 원칙).

## 5. 비기능 요구사항 (Non-Functional Requirements)

### NFR-1. 사용성 (Usability) — 최우선
- NFR-1.1 운전자는 **최소 조작**(이상적으로 무조작/음성 중심)으로 통역을 사용할 수 있어야 한다. 서울 택시 운전자 다수가 60세 이상인 점을 고려한 큰 글씨·직관적 UI.
- NFR-1.2 차량 디스플레이(가로/와이드 레이아웃)에 맞는 Compose 반응형 UI.
- NFR-1.3 운전석 화면은 주행 안전을 위해 정보 밀도를 낮추고 핵심만 표시.

### NFR-2. 성능 (Performance)
- NFR-2.1 발화 종료 후 통역 출력까지의 체감 지연 최소화(온디바이스 처리로 네트워크 의존 최소화).
- NFR-2.2 STT/번역/TTS 파이프라인은 비동기로 UI 블로킹 없이 동작.

### NFR-3. 개인정보/프라이버시 (Privacy)
- NFR-3.1 음성/대화 원문을 영구 저장하지 않는다(세션 종료 시 폐기).
- NFR-3.2 마이크 권한 및 음성 처리에 대한 사용자 동의를 받는다.
- (참고) 심화 보안 확장(Security Baseline)은 이번 범위에서 미적용(공모전 데모 수준).

### NFR-4. 신뢰성/견고성 (Reliability)
- NFR-4.1 STT 인식 실패, 번역 실패, SDK capability 미지원/오류 시 **명확한 오류 상태 표시**와 폴백.
- NFR-4.2 차량 서비스 미연결(일반 Android 환경) 시 통역 기능은 정상 동작하고 차량 데이터는 모사로 대체.
- (참고) Resiliency Baseline 확장은 미적용(PoC/데모 수준).

### NFR-5. 유지보수성/확장성 (Maintainability)
- NFR-5.1 STT/번역/TTS/차량데이터는 **인터페이스로 추상화**하여 엔진 교체·언어 추가가 용이해야 한다.
- NFR-5.2 안내 메시지는 언어별 리소스(strings)로 분리하여 다국어 확장 용이.

### NFR-6. 국제화 (i18n)
- NFR-6.1 승객 언어: 영어, 일본어, 중국어. 운전자 언어: 한국어.
- NFR-6.2 UI 및 안내 메시지는 선택 언어로 표시.

## 6. 제약 사항 (Constraints)
- C-1 Pleos Vehicle SDK는 Pleos 디바이스/에뮬레이터에서만 차량 속성 접근 가능(일반 폰 이미지 불가).
- C-2 ML Kit 온디바이스 번역 언어 모델 최초 1회 다운로드 필요.
- C-3 빌드 환경: JDK 17, Android SDK Platform 35, Gradle.
- C-4 공모전 제출 일정: 1차 기획서 ~11/15, 2차 PT 12월 → 데모 가능한 수준의 핵심 흐름 우선.

## 7. 성공 기준 (Success Criteria)
- SC-1 운전자 한국어 ↔ 승객 EN/JA/ZH 양방향 통역이 좌석 역할별로 분리되어 동작(FR-2).
- SC-2 할증·하차·도착 등 차량 안내가 승객 언어로 적시에 출력되며, 최소 하나 이상의 Pleos Vehicle SDK 도메인(Toll/Door 등)과 연동/폴백 동작(FR-3, FR-5).
- SC-3 첫 발화 언어 자동 인식 또는 수동 선택 + 동의 흐름이 동작(FR-1).
- SC-4 차량 미연결 환경에서도 앱이 크래시 없이 모사 모드로 데모 가능(NFR-4.2).
- SC-5 Android Studio에서 `assembleDebug` 빌드 성공, 에뮬레이터 실행 가능.

## 8. 핵심 요구사항 요약
Taxi-Talk는 **Pleos(Android/Kotlin/Compose) 차량용 앱**으로, **Android 온디바이스 STT/TTS + ML Kit 번역**을 사용해 운전자-승객 간 **좌석 역할 기반 양방향 실시간 통역**을 제공하고, **Pleos Vehicle SDK(Toll/Door/Window/Driving mode/Seat)** 를 활용해 할증·하차·도착 등 차량 안내를 승객 언어로 선제 제공한다. 음성 데이터는 보관하지 않으며, 차량 미연결 시 소프트웨어 모사로 폴백한다.
